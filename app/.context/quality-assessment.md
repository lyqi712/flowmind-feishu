# 飞书知识库核心功能质量评估报告

**评估目标**: 针对新用户核心痛点的功能质量与改进建议  
**评估日期**: 2026-08-14  
**产品**: ima-feishu-copilot (D:/luxiaofei/ima-feishu/app)  

---

## 用户核心痛点

1. **批量文档总结** - 总结多份飞书文档并整合输出
2. **总结质量保证** - 确保总结准确、完整、有引用
3. **知识图谱关联** - 发现不同文档之间的隐含关联
4. **AI 帮写润色** - 写作时 AI 协助与润色
5. **输出到飞书** - 将总结/写作输出回飞书文档

---

## 功能现状评估

### 1. 批量文档总结

#### ✅ 已实现
- **总结 Skill** (`summary`): 提炼文档主题、关键要点与行动项
  - 支持指定 `documentIds` 批量总结
  - 支持主题检索自动选择相关文档（默认最多 6 份）
  - 生成 Markdown 产物，包含核心内容 + 行动建议 + 引用

- **对比 Skill** (`compare`): 横向对比多份材料
  - 提取共同高频词 + 差异矩阵
  - 每份文档的区分词 + 核心描述

- **研究报告 Skill** (`research-report`): 结构化报告
  - 执行摘要 + 关键发现 + 风险限制 + 引用列表

#### ⚠️ 质量问题
```javascript
// server/skills.mjs:159
function summarizeDocument(document) {
  const excerpt = makeExcerpt(document, [], 220);
  return `- **${document.title}**：${excerpt}`;
}
```

**问题**:
1. **固定 220 字符截断**: 长文档只取前 220 字，可能遗漏核心结论
2. **无结构化提取**: 只做文本截取，不识别标题、要点、结论段落
3. **无模型介入**: 完全依赖 `makeExcerpt` 静态截取，没有 AI 提炼
4. **批量上限 6 份**: `selectDocuments` 默认 `limit = 6`，用户想总结 20+ 文档会被截断

#### 📊 实际输出示例（基于代码推断）
```markdown
# "产品规划"材料总结

## 核心内容
- **Q1 产品路线图**：本文档描述 Q1 季度产品规划，包含三个主要方向：用户增长、体验优化和技术债务偿还。具体目标为 MAU 增长 30%...
- **竞品分析报告**：分析了 Notion、Obsidian 和飞书文档三款产品的功能特点。Notion 强在模板生态，Obsidian 强在本地优先...
- **用户访谈记录-0308**：访谈了 5 位企业客户，主要痛点集中在：1. 文档搜索不准 2. 协作冲突频繁 3. 移动端体验差...

## 行动建议
- 回到引用原文核验关键结论。
- 对缺少时间、负责人或量化指标的事项补充上下文。
```

**缺失**:
- ❌ 没有跨文档的**共同主题提炼**
- ❌ 没有**优先级排序**（哪份文档最重要）
- ❌ 没有**冲突检测**（不同文档的矛盾说法）
- ❌ 没有**时间线**（按时间顺序整理事件）

### 2. 总结质量保证

#### ✅ 已实现
- **引用机制**: 每个 Skill 产物都带 `references` 数组
  ```javascript
  references: [{
    index: 1,
    documentId: "xxx",
    title: "文档标题",
    url: "https://...",
    excerpt: "前 220 字..."
  }]
  ```

- **回溯能力**: 笔记/写作的 `sourceRefs` 可以点击回到原文档锚点

- **证据检索**: `retrieval.mjs` 支持语义搜索 + TF-IDF 排序

#### ⚠️ 质量缺陷

**1. 静态截取 vs 语义提炼**
```javascript
// server/skills.mjs:151-154
function summaryArtifact(documents, input) {
  // ...
  '## 核心内容',
  ...documents.map(summarizeDocument), // 只做 makeExcerpt(220)
```

- **现状**: 每份文档只取前 220 字符拼接
- **问题**: 无法识别"结论段落" > "背景说明" 的语义权重
- **对比**: Notion AI / ChatGPT 会先读全文，提取要点，再生成摘要

**2. 模型调用缺失**
```bash
# 搜索 Skill 模块中的模型调用
cd /d/luxiaofei/ima-feishu/app && grep -n "modelService\|generateCompletion" server/skills.mjs
```
结果: **0 条匹配**

- **现状**: `skills.mjs` 完全没有调用 AI 模型
- **问题**: `summary` / `compare` / `research-report` 都是模板拼接，不是 AI 生成
- **影响**: 总结质量完全依赖静态规则，无法处理复杂文档

**3. 批量处理上限**
```javascript
// server/skills.mjs:140
function selectDocuments(documents, { documentIds = [], input = '', query = '', limit = 6 }) {
  // ... 硬编码 limit = 6
}
```

- **现状**: 一次最多总结 6 份文档
- **用户需求**: "很多飞书文档的总结" = 可能 20-50 份
- **改进方向**: 
  - 分批总结（每批 6 份）→ 再总结总结
  - 或提升单批上限到 20（需优化 token 预算）

**4. 引用粒度粗糙**
```javascript
// server/skills.mjs:146
excerpt: makeExcerpt(document, [], 220)
```

- **现状**: 引用只到文档级别，excerpt 是前 220 字
- **问题**: 用户无法快速定位"具体是哪一段支持这个结论"
- **对比**: Perplexity / Bing Chat 的引用可以精确到句子高亮

### 3. 知识图谱关联发现

#### ✅ 已实现
- **图谱构建** (`server/graph/graph-index.mjs`):
  - 文档双链（`[[文档标题]]`）
  - 笔记 sourceRefs（引用关系）
  - 标签关联（共同标签的文档）

- **局部图谱** (本轮新增):
  - 阅读文档时可点击"关联图谱"
  - 以当前文档为中心，显示 1-3 跳关联节点

- **知识观察** (`KnowledgeGraph.jsx:700+`):
  - 为节点生成"核心结论"+"关联观察"+"待验证问题"

#### ⚠️ 关联发现质量

**1. 显式关系 vs 隐含关联**
```javascript
// server/graph/graph-index.mjs:270-290
// 现有图谱只识别:
// 1. 双链 [[title]]
// 2. sourceRefs 引用
// 3. 共同标签
```

**缺失**:
- ❌ **语义相似度**: 两篇都讲"用户增长"的文档，但没有互相引用 → 不会关联
- ❌ **时间关联**: "Q1 规划" → "Q2 复盘" 的时间顺序关系
- ❌ **因果关系**: "需求文档" → "设计方案" → "技术实现" 的依赖链
- ❌ **冲突检测**: "决策 A: 优先移动端" vs "决策 B: 优先桌面端"

**2. 图谱密度问题**
- **新用户场景**: 刚同步飞书，文档间可能没有双链/引用
- **结果**: 图谱是一堆孤立节点，看不出关联
- **改进方向**: 
  - 自动识别"经常一起被搜索"的文档对
  - 基于 TF-IDF 余弦相似度建立弱关联边

**3. 关联推荐被动**
```javascript
// KnowledgeGraph.jsx:700+
// 用户必须:
// 1. 手动点击"知识图谱"
// 2. 手动选择节点
// 3. 手动点击"知识观察"
```

**缺失**:
- ❌ **主动推荐**: 阅读文档时自动提示"你可能还想看..."
- ❌ **路径推荐**: "从 A 到 C，可经过 B → 更清晰理解"

### 4. AI 帮写润色

#### ✅ 已实现
- **智能写作 Skill** (`smart-writing`):
  - 基于知识库证据生成文章/方案/说明
  - 步骤: 理解目标 → 组织证据 → 生成初稿

- **笔记 AI 帮写** (`NotesWorkspace.jsx` + `server/app.mjs:1900+`):
  - 扩写/精简/润色/改写语气
  - 支持选中部分文字操作
  - 预览 → 应用（插入/替换）

- **引用保留**: AI 生成内容会保留 `[1][2]` 引用编号

#### ⚠️ 帮写质量

**1. 提示词固定**
```javascript
// server/app.mjs:1920-1960 (推断位置)
// 帮写提示词可能是:
// "请${action}以下内容：\n${selection}\n\n要求：${tone}、保留引用"
```

**问题**:
- ❌ 没有**领域适配**: 写产品文档 vs 写技术方案的提示词应不同
- ❌ 没有**示例注入**: 优秀案例 → 让模型学习风格
- ❌ 没有**约束规则**: "不要使用被动语态" / "每段不超过 3 句"

**2. 上下文单薄**
```javascript
// 当前帮写只用:
// 1. 选中的文字
// 2. 当前笔记的 sourceRefs
```

**缺失**:
- ❌ **全文上下文**: 选中第 5 段改写，但模型不知道前 4 段讲了什么
- ❌ **风格参考**: "按照我之前写的笔记风格"
- ❌ **术语表**: "这个产品中'用户'特指'企业管理员'"

**3. 批量改写缺失**
- **现状**: 每次只能选中一段改写
- **用户需求**: "润色整篇笔记" → 需要一段一段手动操作
- **改进方向**: "智能润色全文"按钮 → 一键优化

## 关键缺陷分析

### 缺陷 #1: 总结没有真正的 AI（P0）

**现状**: `summary` Skill 只做静态截取，不调用模型
```javascript
// server/skills.mjs:159
function summarizeDocument(document) {
  const excerpt = makeExcerpt(document, [], 220); // 静态截取
  return `- **${document.title}**：${excerpt}`;
}
```

**影响**:
- ❌ 无法提炼要点（只能截断文本）
- ❌ 无法跨文档综合（每份文档独立截取）
- ❌ 无法生成行动项（模板固定）

**用户反馈（预期）**:
> "这个总结就是把前几段复制粘贴了，我自己看文档更快。"

**修复方向**:
1. **引入模型调用**: `summary` Skill 应该像 `smart-writing` 一样调用模型
2. **提示词设计**:
   ```
   你是专业的文档分析助手。请总结以下 {count} 份文档：
   
   {documents}
   
   要求：
   1. 提炼共同主题（2-3 个）
   2. 每份文档的核心结论（1-2 句）
   3. 发现的矛盾或冲突
   4. 可执行的行动项（含负责人/时间）
   ```

3. **分段处理**: 
   - 长文档先分段总结（每 2000 tokens）
   - 再汇总段落总结

### 缺陷 #2: 批量上限太低（P0）

**现状**: 一次最多 6 份文档
```javascript
// server/skills.mjs:140
limit = 6
```

**用户需求**: "很多飞书文档" = 20-50 份

**影响**:
- ❌ 用户勾选 20 份文档 → 只总结前 6 份
- ❌ 无错误提示（用户不知道被截断了）

**修复方向**:
1. **分批总结**:
   ```
   用户选 20 份 → 
   分 4 批（每批 6 份）→ 
   生成 4 个子总结 → 
   最后汇总 4 个子总结
   ```

2. **UI 明确提示**:
   ```
   已选择 20 份文档，将分 4 批总结（预计 2 分钟）
   [ ] 批次 1/4 (完成)
   [ ] 批次 2/4 (进行中...)
   ```

3. **可配置上限**:
   - 模型能力强 → 单批 15 份
   - 模型能力弱 → 单批 3 份

### 缺陷 #3: 图谱关联过于显式（P1）

**现状**: 只有双链/引用/标签才有关联

**用户需求**: "发现隐含关联"

**案例**:
- 文档 A:《Q1 产品规划》提到"用户增长 30%"
- 文档 B:《用户增长策略》详细讲增长方法
- **现状**: 图谱中 A 和 B **没有连线**（无双链/引用）
- **预期**: A 和 B 应该有"主题相关"的虚线连接

**修复方向**:
1. **语义相似度边**:
   ```javascript
   // 伪代码
   for (const [docA, docB] of allPairs(documents)) {
     const sim = cosineSimilarity(embed(docA), embed(docB));
     if (sim > 0.7) {
       graph.edges.push({
         source: docA.id,
         target: docB.id,
         type: 'semantic-related',
         weight: sim
       });
     }
   }
   ```

2. **关联推荐主动化**:
   - 阅读文档 A 时，右侧卡片显示"相关文档推荐"
   - 点击直接跳转，无需打开图谱

// 新增 server/feishu-export.mjs
export async function createFeishuDoc(title, blocks, { tenantToken, spaceId }) {
  const response = await fetch('https://open.feishu.cn/open-api/docx/v1/documents', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${tenantToken}`,

    body: JSON.stringify({
      folder_token: spaceId,
      title,
      content: { blocks: markdownToFeishuBlocks(blocks) }

}

### 总结质量测试

**测试场景 1: 单文档总结**
- 输入: 5000 字产品文档
- 预期: 提炼 3-5 个要点 + 1-2 个行动项
- 评估: 要点覆盖全文 ✅ / 只覆盖前半部分 ❌

**测试场景 2: 批量总结**
- 输入: 20 份相关文档（关于"用户增长"）
- 预期: 
  - 共同主题: 用户增长、留存率、转化漏斗
  - 冲突: 文档 A 说"优先拉新"，文档 B 说"优先留存"
  - 行动项: 3-5 条可执行任务
- 评估: 有跨文档综合 ✅ / 只是拼接 ❌

**测试场景 3: 杂乱文档总结**
- 输入: 1 份包含多个主题的长文档（会议纪要）
- 预期: 按主题分段总结（产品/技术/运营）
- 评估: 结构清晰 ✅ / 混成一团 ❌
